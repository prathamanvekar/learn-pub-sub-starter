SPECIFICATION // ISSUE #01 AMQP 0-9-1 REPOSITORY: bootdotdev/learn-pub-sub-starter SYSTEM: "PERIL" MULTIPLAYER

PERIL ARCHITECTURE SPEC

An engineering explainer of a distributed, asynchronous multiplayer war game built in Go on RabbitMQ. Analyzes direct broadcast fanouts, wildcard topic routing, shared durable queues, competing consumer requeuing, and dual JSON/Gob serialization.

CORE TOPOLOGY SUMMARY: The system decouples a centralized coordinator (cmd/server/main.go:13) from distributed player processes (cmd/client/main.go:14). Nodes interact strictly via an AMQP 0-9-1 broker using two exchanges: peril_direct for administrative broadcast of pause/resume states, and peril_topic for troop movement propagation, distributed war declaration arbitration, and binary game log archival.

1. Broker Dependency

2. Entry Points vs Shared Libraries

The project enforces a strict boundary between protocol mechanics and domain logic:

  • Entry Points (cmd/server/, cmd/client/): Executables that dial AMQP, wire channels, establish subscriptions, and drive terminal user IO.
  • Core Pub/Sub Engine (internal/pubsub/): 100% agnostic of game concepts. Exposes generic Go types to publish and consume arbitrary payloads over AMQP.
  • Routing Schemas (internal/routing/): Canonical routing keys (army_moves, war, pause, game_logs) and wire models (PlayingState, GameLog).
  • Game Domain Engine (internal/gamelogic/): In-memory thread-safe state machine managing units, locations, ranks, and combat resolution algorithms.
ORCHESTRATION TOOL: multiserver.sh:35 allows spawning N concurrent server instances in background processes with a SIGINT process trap to test concurrent cluster behavior.

Player Node & Reactive Handlers

Client Architecture — cmd/client/

Each human participant runs an independent instance of cmd/client/main.go. The client initializes an in-memory thread-safe GameState, binds three specialized subscriptions, and executes commands.

SUB 1: ARMY MOVES TRANSIENT

Exchange: peril_topic
Queue: army_moves.<username>
Key: army_moves.*

Listens for troop movements from all players. When a foreign player moves into a sector occupied by the local player, handlerMove detects the collision and fires a RecognitionOfWar event (handlers.go:23).

QUEUE TYPE: Transient (auto-deleted upon client exit).
SUB 2: WAR DECLARATIONS DURABLE // SHARED

Exchange: peril_topic
Queue: "war"
Key: war.*

Competing Consumers Pattern: All clients subscribe to the exact same queue named "war". If a client receives a war declaration where it is neither the attacker nor the defender, it returns NackRequeue (handlers.go:50) so the broker re-delivers it to the actual combatant!

QUEUE TYPE: Durable with Dead-Letter Exchange.
SUB 3: PAUSE STATE TRANSIENT

Exchange: peril_direct
Queue: pause.<username>
Key: pause

Direct broadcast listener. Dispatches to handlerPause (handlers.go:93), which sets gs.Paused = true/false under a write-mutex, preventing troop movements while the game is frozen.

QUEUE TYPE: Transient (unique per username).

THE COMPETING CONSUMERS WAR ARBITRATION ALGORITHM cmd/client/handlers.go:44-86 
func handlerWar(gs *gamelogic.GameState, publishCh *amqp.Channel) func(gamelogic.RecognitionOfWar) pubsub.Acktype {
    return func(dw gamelogic.RecognitionOfWar) pubsub.Acktype {
        defer fmt.Print("> ")
        warOutcome, winner, loser := gs.HandleWar(dw)

        switch warOutcome {
        case gamelogic.WarOutcomeNotInvolved:
            // Message was round-robined to an uninvolved client -> put back on queue!
            return pubsub.NackRequeue

        case gamelogic.WarOutcomeNoUnits:
            // Malformed war state (no units at location) -> drop from queue
            return pubsub.NackDiscard

        case gamelogic.WarOutcomeOpponentWon, gamelogic.WarOutcomeYouWon, gamelogic.WarOutcomeDraw:
            // Combat resolved! Attacker logs results using binary Gob serialization
            err := publishGameLog(publishCh, gs.GetUsername(), fmt.Sprintf("%s won a war against %s", winner, loser))
            if err != nil {
                return pubsub.NackRequeue
            }
            return pubsub.Ack
        }
        return pubsub.NackDiscard
    }
}

Engineering Quick Reference

Key Concepts Cheat Sheet

EXCHANGE TYPES peril_direct vs peril_topic
Direct Exchange (peril_direct): Delivers messages strictly by exact key equality. Used for "pause". Each client creates its own unique transient queue (pause.<user>) bound with key "pause". This converts the direct exchange into a broadcast fanout.

Topic Exchange (peril_topic): Routes messages based on wildcard dot-delimited tokens. Used for army_moves.*, war.*, and game_logs.*. Allows subscribers to selectively filter or receive entire event classes.
QUEUE DURABILITY Durable vs Transient
SimpleQueueDurable: durable = true, auto_delete = false, exclusive = false. The queue metadata and persisted messages survive broker reboots. Used for war and game_logs.

SimpleQueueTransient: durable = false, auto_delete = true, exclusive = true. Bound exclusively to a single client connection. When that player exits or crashes, the broker instantly garbage-collects the queue, avoiding orphaned queues.
ACKNOWLEDGMENT STRATEGY Ack, NackDiscard, NackRequeue
Ack (msg.Ack(false)): Message was successfully consumed and processed. Broker deletes it.

NackDiscard (msg.Nack(false, false)): Message was malformed, corrupted, or invalid (e.g. no troops present in sector). The message is dropped from the active queue and forwarded to peril_dlx.

NackRequeue (msg.Nack(false, true)): Handshake failed or client was uninvolved in combat. RabbitMQ places the message back onto the head of the queue for another consumer to process.
DEAD-LETTER EXCHANGE peril_dlx
Declared via AMQP header table amqp.Table{"x-dead-letter-exchange": "peril_dlx"} during QueueDeclare (consume.go:96). Prevents poisonous message discard by routing unhandled failures to a secondary sink for administrative forensics.
DUAL SERIALIZATION JSON vs Gob
JSON (application/json): Used for player-facing commands (PlayingState, ArmyMove, RecognitionOfWar). Interoperable, human-readable, and standard.

Gob (application/gob): Go's native binary stream serialization (publish.go:23). Used exclusively for GameLog telemetry, offering fast zero-boilerplate serialization of Go types and time.Time objects without schema drift.
CONNECTION VS CHANNEL AMQP Concurrency
Connection (amqp.Connection): Represents a single underlying physical TCP connection between process and broker. Heavyweight to negotiate; persistent throughout the process lifetime.

Channel (amqp.Channel): A lightweight virtual multiplexed sub-connection inside the TCP stream. The Peril codebase allocates a distinct dedicated channel for publishing (publishCh) and separate channels for each background consumer goroutine (consume.go:85), preventing thread contention.
